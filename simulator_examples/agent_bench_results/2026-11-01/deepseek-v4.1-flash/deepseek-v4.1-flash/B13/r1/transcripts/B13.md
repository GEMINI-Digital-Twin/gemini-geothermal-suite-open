        """Heat rejected to air; zero when the water is not warmer than the air."""
        p = self.parameters
        c_water = p["water_density"] * p["water_cp"] * u["water_flow_rate"]

        self.output = {

            "fan_power": p["fan_power_fraction"] * q,

        }

**What the bug was:** a division by zero at zero water flow. The effectiveness line

```python
eff = 1.0 - math.exp(-p["ua"] / c_water)
```

was evaluated *before* any flow guard, and `c_water = density * cp * flow` is exactly 0 when `water_flow_rate = 0`. So the model raised `ZeroDivisionError` instead of returning "no heat rejected". The only guard in the original code was on the `t_out` line (`q / c_water if c_water > 0 else 0.0`), which is too late — the crash happens one line earlier.

**Why the intern's tests didn't catch it:** all three tests use a non-zero flow (0.3 m³/s). Zero flow — the case the harness explicitly checks ("no heat when the flow is zero") — was never exercised, so the suite passed while the model was broken.

**The fix (plus two hardening points):**
- One guard up front: if `flow <= 0`, `ua <= 0`, or `t_in <= t_air`, return `eff = 0`, `q = 0`, `t_out = t_in` — no division at all.
- Effectiveness clamped to [0, 1] and `t_out` clamped to `[t_air, t_in]`, so the second-law check cannot be violated by round-off.
- Added tests for zero flow and for the monotonic trends the harness checks (heat rises with inlet temperature and flow, falls with air temperature).

The physics itself was sound: NTU-effectiveness with the water side as C_min (air treated as an infinite sink, C_r = 0) is the right formulation for a dry cooler, and `q = eff · C_water · (T_in − T_air)` with `T_out = T_in − q/C_water` satisfies the energy balance.
